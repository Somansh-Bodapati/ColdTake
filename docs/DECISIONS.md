| Cricket data vendor (doc 02 §4.2, session 11 → verified session 15) | Session 11 built `CricketDataProvider` against a *guessed* response shape (no vendor account existed then). A real account/key now exists and every fact below is verified against real, live calls, not reconstructed: base URL `https://api.cricapi.com/v1/`, auth via query param `?apikey=<key>` (not a header), every call also sends `&offset=0`. **Hard constraint: 100 requests/day, free tier**, reported back on every response via an `info.hitsToday`/`info.hitsLimit` block — CricketDataProvider watches this itself and `console.warn`s once usage crosses 80% (no separate persisted rate tracker needed, the API already reports its own usage). This drove two changes: (1) `getTable` calls `series_info` exactly once per invocation — that single call embeds a series' full match list, so there's never a per-match call for routine table computation; (2) `.github/workflows/ingest-cron.yml`'s schedule moved from every 30 minutes (48 calls/day for one tournament — nearly half the account's entire daily budget on its own) to every 3 hours (8 calls/day), leaving headroom for more tournaments and manual/admin-triggered ingestion or settlement. Two permanent (not temporary) gaps on this tier, confirmed live: **no player-level batting/bowling stats anywhere** (`match_info`'s `score` field is innings-level runs/wickets/overs only) — `getStatLeaders` always returns `[]`, so stat_leader questions on a cricketdata-sourced tournament require manual entry (ManualProvider / the manual-standings admin flow); and **no reliable signal for a tournament's actual champion** (`matchType` is a format like "test"/"odi"/"t20", not a stage — a final/playoff can't be told apart from an ordinary league match) — `getFinalResult` always throws a typed `ProviderUnsupportedError`, and champion/runner-up questions are settled through Session 12's manual settlement + admin-override flow instead. |

| Vercel/Neon accounts | Not provisioned yet. Local dev uses a Dockerized Postgres; `DATABASE_URL` swaps to a real Neon connection string at deploy time — schema/queries stay driver-compatible (`@neondatabase/serverless` over plain `pg` for local) |
